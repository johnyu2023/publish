标题：双 Agent 编程工作流
描述：构建可验证的 AI 辅助编程工作流：规范驱动、角色分工与独立审核
发布日期：2026/11/05
标签：
AgentSDDCodexClaude Code

AI 辅助编程可以加快实现，但在复杂项目中，仅靠连续对话推进开发，容易出现需求遗漏、实现偏离和验收依据不清的问题。

一种值得尝试的工作流是：先形成明确的任务规范，再分阶段实现，并安排未参与实现过程的 Agent 进行独立审核。本文以 Codex 和 Claude Code 为例介绍这种协作方式，同时说明它的适用条件与局限。

这是一种工程实践选择。它是否有效，需要结合项目规模、交接成本和实际缺陷情况判断。

一、以规范组织开发，并保留反馈循环 ​

规范驱动开发（Specification-Driven Development，简称 SDD）的核心，是让明确、可检查的规范持续指导实现与验收。GitHub Spec Kit 就提供了从规范、计划、任务到实现与收敛的流程支持。参考：GitHub Spec Kit

在 AI 辅助开发中，可以采用以下步骤：

  1. 对齐需求：明确目标、使用场景、范围和不做什么。
  2. 形成任务规范：记录行为要求、接口约束、关键边界和验收标准。
  3. 拆分阶段：将任务分成范围可控、能够独立验证的小阶段。
  4. 实施与验证：根据规范修改代码，并执行相应检查。
  5. 审核与收敛：核查需求覆盖、代码正确性和兼容性，处理有证据的问题。

规范不应只是编码前生成的一份文档。实现过程中如果发现技术限制、需求冲突或遗漏，应回到规范中澄清，再同步调整任务和验收标准。

流程的严格程度也应与任务匹配。简单缺陷修复可能只需要问题描述、复现步骤和验收条件；涉及多个模块的功能，通常需要更完整的设计与交接材料。

二、角色分工比固定工具组合更重要 ​

一种可行的分工是：

  • 开发者：确定业务目标、解决需求歧义，批准重要设计与最终结果。
  • 规划 Agent：协助分析现有实现、整理规范、拆分阶段和生成交接提示词。
  • 实现 Agent：完成代码修改、测试和实现记录。
  • 审核 Agent：依据规范、代码与运行证据，检查遗漏和缺陷。

例如，可以让 Codex 协助规划与审核，让 Claude Code 负责实现。也可以交换工具，或使用同一种工具中的不同会话承担不同角色。

这种分工的价值，在于明确每个角色的任务和交付物。不能仅凭产品名称，就认定某个工具天然适合架构、另一个工具只适合执行。

同时，角色分工也有成本：规范需要维护，交接可能丢失信息，多个 Agent 可能重复阅读和运行检查。应根据实际收益决定是否采用完整流程。

三、区分测试验证与测试驱动开发 ​

Agent 生成并运行测试，并不自动意味着它采用了 TDD。

如果先完成业务代码，再补充测试，这通常属于实现后的测试验证。它依然有价值，但不能仅凭“有测试且测试通过”就称为测试驱动开发。

TDD 强调反复进行小步的 Red → Green → Refactor：

  1. Red：为下一个预期行为编写测试，并确认它因预期原因失败。
  2. Green：实现使测试通过的最小必要改动。
  3. Refactor：必要时重构代码与测试，保持已有测试通过。

这不是先写完一个阶段的全部测试，再集中实现。测试顺序、反馈速度和重构同样重要。参考：Martin Fowler 对 TDD 的说明

如果希望 Agent 采用这种方式，可以使用以下指令：

每次选取一个可验证行为，先编写测试并运行，确认失败与待实现行为有关，而非无关的环境问题。随后完成最小必要实现；必要时重构并保持测试通过，再进入下一个行为。记录实际执行的命令和结果。

提示词只能表达要求，不能代替执行证据。审核时仍应检查测试是否覆盖需求、断言是否有效，以及测试通过是否依赖不合理的模拟或实现细节。

是否采用 TDD，也应结合任务性质判断。探索性原型、界面调整和外部系统集成，可能需要其他验证方式配合。

四、采用上下文隔离的独立审核 ​

实现完成后，可以让一个未参与实现讨论的新会话或独立子代理审核代码。

Claude Code 官方文档介绍了类似做法：由未看到实现过程的会话或子代理检查变更，再将发现反馈给实现方。参考：Claude Code 最佳实践

这种方式的潜在收益，是减少此前讨论、实现解释和既有结论对审核的影响，让审核者重新检查证据。

但必须区分以下概念：

  • 上下文隔离不保证无偏见。审核者仍可能受到错误规范、提示词和模型自身偏差影响。
  • 新会话不等于双盲测试。没有建立明确的信息隐藏和实验安排，就不宜使用“双盲”描述。
  • 它不等同于 Cleanroom 软件工程。后者包含数学化规范、正确性验证和统计测试等明确方法，不能仅凭创建新会话就套用这个名称。参考：CMU SEI 的 Cleanroom 定义

因此，本文使用“上下文隔离的独立审核”这一描述。

隔离讨论历史，保留必要事实 ​

独立审核的目标不是让审核者缺少背景。审核者除了 Spec，还需要检查现有接口、项目规则、调用关系和兼容性约束。

OpenAI 的 Codex 审核说明也强调了项目背景的重要性，例如旧接口契约、数据处理规则和跨服务影响。参考：Codex 自定义审核规则

审核交接至少应明确：

  • 当前阶段的规范、范围和验收标准；
  • 仓库位置、审核基线和待审核变更；
  • 必须保留的既有行为与接口约束；
  • 已执行的验证及其结果；
  • 未执行项、已知限制和待确认问题。

对于能够读取仓库的 Agent，通常提供准确路径和阅读入口即可，不必将全部代码一次性粘贴进提示词。

还要确认审核者看到的是正确版本。如果待审核内容包含未提交改动，新会话应能读取这些改动；如果使用隔离工作区，应显式核对起始提交及待审核变更，避免审核了错误基线。

五、让审核结论建立在证据上 ​

独立审核可以暴露规范中的歧义，但不能把所有误报都归因于规范不清晰。

审核提出问题时，可能存在多种情况：

  • 实现确实违反了需求或现有契约；
  • 规范遗漏或存在冲突；
  • 审核者遗漏了代码路径或运行条件；
  • 审核者读错版本，或推理本身有误。

因此，每项审核发现应尽量说明：

  1. 问题所在的文件和位置；
  2. 触发问题的具体条件；
  3. 违反的需求、契约或预期行为；
  4. 可复现步骤、测试或其他证据；
  5. 对使用者或系统造成的实际影响。

对于证据不足的发现，可以要求补充核查。对于成立的问题，应修复实现或澄清规范；对于误报，应记录驳回理由。

同一审核会话可以继续跟进返修，检查原问题是否解决、修改是否引入回归。若变更范围明显扩大或需要重新检查整体结果，也可以再安排一次独立复核。

停止返修的依据应是验收标准得到满足、相关缺陷得到处理、剩余限制得到确认。反复要求 Agent “继续找问题”，可能导致无必要的改动。

六、把上下文管理视为信息管理 ​

长对话可能累积过期方案、重复输出和不再相关的信息。研究与工程实践表明，长上下文可能影响模型的信息检索和推理精度，但影响程度取决于模型、任务与内容。参考：Anthropic 上下文工程说明

新会话可以减少历史上下文负担，但不会提高模型本身的上下文窗口上限，也不保证整个工作流消耗更少的 Token。

可采用的管理方式包括：

  • 将已确认需求和决策写入可维护的文档；
  • 将任务拆成能够独立验证的阶段；
  • 通过摘要或上下文压缩保留关键状态；
  • 提供文件索引，让 Agent 按需读取；
  • 在阶段切换时明确当前版本、未解决问题和验证结果。

核心原则是：保留与当前任务有关的事实，减少重复与过期信息，同时避免丢失关键约束。

七、如何判断这套流程是否值得使用 ​

规范、角色分工和独立审核可以帮助组织复杂任务，但流程更多不代表质量必然更高。

如果希望验证其收益，可以在相近任务中记录：

  • 开发与交接耗时；
  • 总体调用成本；
  • 审核发现中真实缺陷与误报的情况；
  • 返修次数及原因；
  • 验收后仍然出现的遗漏或回归。

在缺少这些证据时，更合适的结论是：

对需求复杂、需要分阶段交接的项目，以明确规范组织实现，并安排未参与实现过程的 Agent 复核，是值得尝试的工作流。其效果取决于规范质量、交接材料、测试证据和开发者判断。新会话可以减少部分历史讨论的干扰，但不能保证审核正确，也不能替代最终验收。
