> + **Prompt Engineering（提示工程）** - “说服”模型 - Prompt 决定了下限
> + **Context Engineering（上下文工程）** - “武装”模型 - Context 决定了准确度
> + **Harness Engineering（外壳/装具工程）** - “约束”模型 - Harness 决定了系统的可用性和存活率

## 3个概念的对比

### 核心概念与区别对比

| 工程维度 | 核心关注点 | 解决的问题 | 现实世界类比 |
| :--- | :--- | :--- | :--- |
| **Prompt Engineering** | **指令的表达方式**：优化输入词汇、语气、逻辑链（如 Few-shot, CoT）。 | 模型“听不懂”或“不知道怎么按步骤思考”。 | **经理给交易员下发任务书**：把“给我选个好股票”变成“按 MA20 突破策略，寻找量比大于 2 的标的”。 |
| **Context Engineering** | **信息的供给质量**：RAG（检索增强生成）、Schema 注入、历史数据加载。 | 模型“不知道当前的客观情况”或产生幻觉。 | **给交易员递交最新的研报和行情**：把数据库表结构、最新的 Level-2 Tick 数据切片放在他桌面上。 |
| **Harness Engineering** | **运行环境与闭环控制**：沙箱、错误重试机制、安全护栏、输入输出拦截。 | 模型“乱来”、“出错后卡死”或“破坏系统环境”。 | **给交易员配备合规风控系统与自动下单机**：哪怕他下达了“满仓买入”的疯狂指令，风控拦截器也会直接将其熔断并打回重做。 |

### 在一个简单量化系统中的实战举例

假设我们正在开发一个自动化的选股模块：系统每天收盘后，让 AI Agent 查阅当天的 Level-2 数据，并生成一段代码来筛选出明天可能高开的 A 股标的。

#### 1. Prompt Engineering (提示工程)：教导规则
这是最基础的交互。我们在代码中固化一段精调的 Prompt。

+ **做法**：`"你是一个资深 A 股量化研究员。请使用 Polars 编写一个选股逻辑，要求过滤出当天尾盘有资金抢筹的股票。注意：只需返回代码，不要解释。"`
+ **局限**：模型可能会自己捏造一个不存在的 Polars 函数，或者不知道你的数据列名是什么。

#### 2. Context Engineering (上下文工程)：注入现实
为了防止模型瞎编，我们需要在 Prompt 之外，将真实的业务上下文打包喂给它。

+ **做法**：在发送请求前，系统先通过查询本地数据库，把表结构动态拼接到上下文中。

    ```text
    // 注入的 Context
    当前的 Tick 级别数据表名是 `ticks_sh`，存放在 DuckDB 中。
    核心列包括：`symbol` (varchar), `price` (float), `volume` (int), `bid1_volume` (int)。
    ```

+ **效果**：此时模型生成的代码，就会精准地使用 `bid1_volume` 这个字段来进行过滤，大大降低了代码运行报错的概率。

#### 3. Harness Engineering (外壳工程)：构建护栏与自愈闭环
这是让系统真正达到工业级稳定性的关键。即使有了上述两步，AI 依然可能生成包含语法错误、死循环，或者带有违规操作的代码。Harness 就是包裹在 AI 外层的一层“安全装甲”。

+ **做法**：
    1. **沙箱隔离**：Harness 接收到 AI 生成的代码后，绝不在宿主机的原生环境中直接 `exec()`，而是将其放入一个隔离的 **Built-in Python** 运行环境中执行，避免与系统底层依赖产生冲突。
    2. **合规性拦截**：Harness 包含静态分析工具，检查 AI 是否尝试生成写入中文文件名的日志（例如 `选股日志.log`）。如果发现，Harness 并在代码执行前直接报错拦截，强制要求修改为跨平台兼容的英文格式（如 `stock_selection_output.log`）。
    3. **自愈闭环 (Feedback Loop)**：当隔离环境中的代码抛出异常（例如除以零），Harness 不会让整个 FastAPI 后端崩溃，而是捕获这段 Traceback 错误，附带上一句 `"你的代码在 Built-in Python 中运行失败，请根据此错误日志修复"`，然后重新扔回给大模型。
    4. **接口约束**：在通过 ZeroMQ 将最终选股结果推送到 QMT 交易终端前，Harness 会对数据格式进行最后一次强校验。

## Harness Engineering 实践

> Harness Engineering（或者叫 AI 驱动/任务驱动开发）

+ 这种模式本质上是把你的角色从“一线码农”拔高到了“系统架构师”和“代码审查员（Reviewer）”。对于一个由多个 AI 参与、且需要精打细算 Token 的工程来说，这是最成熟、最不容易失控的打法。
+ 表面上看，写 MD 文件多花了几分钟，但它彻底消灭了“AI 幻觉乱改代码导致的 debug 地狱”，也让你随时能掌控系统的全貌，而不是被 AI 牵着鼻子走。

+ 未来的日常开发，标准 SOP（标准作业程序）就是这样的三步走：

### 第一步：起草契约（编写 Markdown 任务书）
不要直接在聊天窗口里长篇大论，而是在 `docs/tasks/` 下新建一个结构化的 MD 文件。
这个文件就是你（架构师）和 AI（外包小弟）之间的**契约**。里面必须包含：

+ **上下文**：要改什么，为什么改。
+ **具体边界**：明确告诉 AI 改哪些文件，**绝对不能碰哪些文件**。
+ **硬性约束**：这是体现你工程习惯的地方。比如你可以把“**必须保留原有对接口的探嗅代码和注释，以便后续调试**”或者“**新生成的日志文件绝对不能包含中文命名**”这种铁律直接写在任务书的顶部。

### 第二步：智能路由（分发给合适的 AI）
有了 MD 文件，你就可以做“算力统筹”了：

+ **派给 Lingma IDE**：像数据库简单 CRUD、编写单次执行的 Python 脚本、简单的 FastAPI 路由扩充、或者整理文档。让它做“体力活”，错了成本也低。
+ **派给 Claude Code**：如果涉及到复杂的 React 状态流转、QMT 环境下复杂的 ZMQ 数据流转发，或者重构核心的量化数据处理逻辑，再用这把“牛刀”。

### 第三步：人工验收（QA 与合并）
AI 汇报“已完成”后，**你绝对不能盲目信任，必须手工确认**。但你的确认方式不是逐行去读它写的每一句代码，而是：

1. **看 Git Diff**：用 Git 工具看它到底改了哪些文件。如果任务是改数据库，它却莫名其妙改了前端路由，立刻回退（Revert）。
2. **跑一遍主流程**：启动后端和前端，实际点一下页面，确认需求是否跑通。
3. **闭环文档**：测试通过后，把你写的这个 `update_guest_login.md` 从 `docs/tasks/` 移动到 `docs/tasks_archive/`（归档），或者直接删除，保持任务目录的整洁。
