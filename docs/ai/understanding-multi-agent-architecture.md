## 引言

在大模型应用日益复杂的今天，单个 Agent 越来越难以胜任需要多步骤推理、多工具调用、多角色协作的任务。于是「多 Agent 架构」成为了热门话题——但多 Agent 不是银弹。拆得好，事半功倍；拆不好，反而引入更多复杂度和成本。

本文将从「为什么要拆」「怎么拆」「怎么通信」「结果如何汇总」「工程上要管住什么」五个维度，系统梳理多 Agent 架构的设计思路与实践经验。

## 一、为什么要拆：单 Agent 的四个瓶颈

一个 Agent 的核心循环是：模型读上下文，决定调哪个工具，把结果放回上下文，再决定下一步。任务一复杂，这个循环就会在四个地方卡住。

### 1. 上下文被中间结果塞满

查日志、搜代码、翻网页——读进来的东西大多只用一次，却一直占着上下文，也分散了模型对任务本身的注意力。一个子 Agent 探索时可能用掉几万 token，但交回主 Agent 的往往只是一两千 token 的摘要。

**隔离上下文**是拆分的首要理由之一：让做了大量探索的 Agent 在自己的沙盒里工作，不要让它污染指挥部的上下文。

### 2. 工具太多、太相似，选不准

工具数量本身不是问题，问题在于工具之间是否相似、重叠。有的系统能用好 15 个以上界限清楚的工具，有的不到 10 个互相重叠的工具就开始选错。当工具数量多到模型频繁选错时，按领域拆给不同的 Agent 是有效的解法。

### 3. 一个提示词里塞了太多分支

规则里全是「如果……就……否则……」，改一处牵动别处。还有一种常见问题是**角色冲突**：同一个上下文里既写代码又审代码，审的时候带着写的时候的假设，很难看出自己的错。把不同职责拆给不同 Agent，能从根本上解决这个问题。

### 4. 互不依赖的子任务只能串行执行

查五个竞品、看十个模块——单 Agent 只能轮流来，每做完一件，上下文里就多一堆材料。让主 Agent 一次派出多个子 Agent 同时搜索，每个子 Agent 也同时调多个工具，复杂问题的研究时间最多可以缩短九成。

**这四种情况，拆的理由各不相同**：前两种是隔离上下文和工具，第三种是分开职责，第四种才是并行。理解这些区别，比简单地说「任务复杂所以拆」要有说服力得多。

## 二、多 Agent 的代价

拆分不是免费的。多 Agent 架构会引入以下几类额外成本：

- **Token 成本**：Agent 的 token 用量一般是普通对话的 4 倍左右，多 Agent 系统可达 15 倍。多 Agent 表现更好的一部分原因，来自它能把更多 token 花到任务上。
- **协调开销**：主 Agent 要拆任务、写任务说明、读报告、核对版本、纠正工具给出的错误结论。
- **信息丢失与决策冲突**：子 Agent 各自只看到自己那一块，各自的决定说得通，放在一起却对不上。共享上下文、共享完整的过程记录，是避免这类问题的关键。
- **错误累积**：一个 Agent 的错误结论，到了下游就成了已知事实。Agent 有状态，错误会累积。

## 三、什么任务值得拆

以下几类任务适合拆成多 Agent：

- **子任务之间依赖少**，可以各做各的，比如广度优先的调研、几个来源分头检索、按模块分头审查。
- **过程很长、结论很短**，比如读大量日志、翻代码，最后只要一个结论。
- **需要不同的工具或权限**，比如只读的检索和能写的执行。
- **需要一个没参与过程的人来检查**。
- **任务够值钱**——多 Agent 只适合价值高到付得起额外开销的任务。

以下几类任务**不适合拆**：

- 各部分强依赖，要共享同一套决策。
- 一个 Agent 几步就能做完的任务。
- 流程固定、每一步都能写死的任务——用 Workflow 更稳。

### Agent 还是 Skill？

区分这两个概念很重要：

- **Skill** 是一份做事的说明，可以带上脚本和资料，用到时加载进当前 Agent 的上下文。活还是这个 Agent 在干，上下文和权限都是同一套。
- **子 Agent** 是另起炉灶：每个子 Agent 在自己的上下文窗口里运行，有自己的系统提示词、可用工具和独立的权限，做完只把摘要交回主对话。

简单说：缺的是「会不会做」，加 Skill；缺的是「做的时候别把主上下文弄乱」「要用不同的权限」「要一个独立的检查者」「要并行跑好几轮」，才拆成 Agent。

## 四、怎么拆：结构、边界与任务说明

### 4.1 几种常见结构

| 结构 | 描述 | 适用场景 |
|------|------|----------|
| **主从（Manager）** | 一个主 Agent 拆任务、派活、汇总，子 Agent 只对主 Agent 负责 | 需要一个 Agent 掌控流程、最后综合结果的任务 |
| **流水线** | 按阶段排好，一个 Agent 做完交给下一个 | 步骤固定、顺序明确的流程 |
| **并行分片** | 同一类任务切成几份，几个子 Agent 各做一份，再合并 | 长文档按章节切开各自抽取，再汇总 |
| **执行加审查** | 一个干活，一个检查，不通过就打回 | 需要质量保障的生成任务 |
| **按意图转交** | 前台分诊 Agent 判断用户要什么，把对话交给对应专职 Agent | 客服等不需要居中掌控的场景 |

主从结构还可以嵌套：主 Agent 下面是编排 Agent，编排 Agent 下面是原子 Agent。每多一层就多一次转述和等待，只有下面的 Agent 多到一个主 Agent 管不过来，或者各层权限确实不同时，才值得加。

### 4.2 按什么边界拆

好的拆分边界应该满足：

- **上下文边界**：子 Agent 拿着一份任务说明就能干完，不需要知道主 Agent 之前的全部讨论。
- **工具和权限边界**：只读的和能写的分开，碰生产数据的单独一个。
- **能单独验收**：子 Agent 的产出要能单独检查，比如测试是否通过、文件是否生成、结论有没有出处。

「按职位起名」不等于找到了边界。「产品经理 Agent」「架构师 Agent」「程序员 Agent」如果读的是同一批材料、做的是互相依赖的决定，拆完只是多了几次转述。

### 4.3 预定义还是动态创建

- **预定义**：每种子 Agent 的提示词、工具和权限提前写好，主 Agent 只决定派谁、派什么任务。好处是行为可预期、好测试。
- **动态创建**：主 Agent 临场写任务说明，自己决定派几个。灵活，但要有上限。

常见做法是两者结合：子 Agent 的类型预先定义，具体任务动态下发。

### 4.4 给子 Agent 的任务说明

子 Agent 从一个干净的上下文开始，看不到主 Agent 之前聊过什么。任务说明至少应写清六样：

1. **要交付什么**
2. **做什么、不做什么**，和别的子 Agent 怎么分界
3. **已经确认的事实和相关文件的路径**，免得重查
4. **用哪些工具**，优先看哪些来源
5. **交回的格式**
6. **做到什么程度算完成**，最多花多少步、多少 token

检验办法很简单：把这份说明交给一个没参与讨论的新同事，他能不能直接开工。

### 4.5 子 Agent 能不能再派子 Agent

嵌套是允许的，但需要管控：

- **深度限制**：最深到主对话下面第三层，层数可配置。
- **并发数限制**：同一个会话里同时运行的子 Agent 有上限。
- **预算限制**：整棵树共用预算，子 Agent 继承的是剩余预算。
- **循环检测**：每次派生都带上祖先链，记下谁派的谁，派之前检查有没有绕回去。
- **兜底策略**：全局的步数和时间上限。

## 五、怎么通信：三种模式

### 5.1 经主 Agent 中转

子 Agent 只和主 Agent 说话，彼此看不见。好处是好控制、好追踪；代价是主 Agent 成了瓶颈，所有报告都要进它的上下文。

### 5.2 共享状态（黑板模式）

大家读写同一块存储，比如一张任务表、一个状态对象、一个共享目录。子 Agent 之间不用直接对话，看黑板就知道进度。要管住的是写入：一个任务只能被一个 Agent 认领；同一份数据只有一个权威副本，写入带版本，冲突能被发现。

### 5.3 直接对话或转交

A 直接给 B 发消息，或者把整个对话交给 B。这种模式灵活，但要有明确的规则，比如由一个协调者指定下一个轮到谁。没有规则的群聊最容易抢答。

### 5.4 路由：派给谁

主 Agent 或路由节点要决定一件事交给哪个子 Agent，可以用规则、分类模型，或者让大模型按各个子 Agent 的说明来选。无论哪种方式，都要做到：

- 说明写清负责什么、不负责什么，彼此不能重叠
- 准确率靠评测持续提升
- 给路由留一个「拿不准」的出口
- 派错了要能退回

### 5.5 A2A 与 MCP 的分工

当 Agent 由不同团队、不同厂商开发、分开部署时，需要协议来连接它们：

- **MCP（Model Context Protocol）**：把每个 Agent 连到它自己的工具。调 MCP 的工具像调函数，输入输出确定，工具自己不做判断。
- **A2A（Agent2Agent）**：把 Agent 彼此连起来。通过 A2A 找的是另一个 Agent，它有自己的模型、工具和记忆，对你是个黑盒，可能跑很久，中途还会回头问你要信息。

简单说：Skill 是 Agent 自己的做事方法，MCP 接的是它手边的工具，A2A 是把活交给另一个 Agent。

## 六、结果汇总与冲突处理

### 6.1 汇总：只用交回来的东西

并行分片时，子 Agent 要按统一格式交结果，带上出处。汇总按字段合并、去重、标出冲突，不要把几份报告丢给模型自由改写。

主 Agent 汇总时容易出现幻觉——报告太多太长导致漏看或看混、模型用自己的知识补空缺、转述时改了数字和限定词、几份报告有冲突被揉成了一个读起来通顺的说法。约束方法：

- 每条结论都标出来自哪个子 Agent 的哪条证据，标不出来的不写
- 汇总后加一道核对，逐条检查结论在子 Agent 的结果里有没有依据
- 关键的数字和名称照抄，不让模型改写
- 汇总这一步不给检索工具，免得它半路自己找新材料

### 6.2 两个 Agent 说法矛盾

当两个执行 Agent 对同一个业务事实给出了矛盾的结果时：

1. **先确认是不是真冲突**：时间点不同、统计口径不同、数据来源不同，都会让两个说法看起来矛盾。
2. **再按规则采信**：权威数据源优先于文档，文档优先于模型推断；新版本优先于旧版本；有证据的优先于没证据的。
3. **规则判不了就去查**：直接调权威系统核实，或者派一个 Agent 专门复核；还判不了，交给人。
4. **冲突写进结果里**：不能让汇总的模型自己挑一个了事。

也可以用投票：让几个 Agent 做同一件事，少数服从多数。但投票只在各自出错的原因互不相关时才有用——用的是同一个模型、读的是同一份错误资料，几票会一起错。

### 6.3 Critic：检查要有依据

Critic 检查最好有客观依据：测试能不能过，格式对不对，每条结论有没有出处，需求清单上的项做没做到。主观的部分，用评分标准让模型打分。

Critic 最好有独立的上下文，只看需求和产出，不看执行者的推理过程；能接上测试结果、工具返回这类外部信号更好；条件允许，可以换一个模型。

不通过以后，Critic 要给出具体的问题和证据：哪条测试没过，哪条结论缺出处。执行者按清单改，而不是整个重做。防止反复循环可以设最多轮数、连续两轮问题数没有减少就停、整体预算到线也停。

### 6.4 防止幻觉放大

在一条链路上，上游的一句猜测，到了下游就成了已知事实，再往下传，就没人记得它没验证过。防止幻觉放大的办法：

- 让证据跟着结论走：结论和出处一起传，没有出处的标「未核实」
- 下游把上游的输出当成说法，而不是事实
- 关键事实在交接处核对一次
- 最终的引用能追到原始出处

## 七、工程上要管住的几件事

### 7.1 子 Agent 失败与超时

- 每个子 Agent 设超时和步数上限
- 偶发错误自动重试，次数有限；同样错误反复出现就别再试
- 失败了也带着做完的部分返回，写清楚做到哪一步、哪些还没核实
- 长任务要能续跑，从出错的地方恢复而不是从头再来
- 有副作用的操作（写库、发消息、下单）要幂等

多 Agent 的成功率是一环一环乘出来的：五个环节各有 95% 的成功率，互相独立、出错也不重试的话，整体只有 77% 左右。

### 7.2 预算要覆盖所有 Agent

预算只写在题面里是不够的。主 Agent 和子 Agent 都只看得到自己那一部分，总量得由运行系统统一汇总，到线就停。做法是开工前给各个子 Agent 留出份额，运行时持续累加主 Agent 和所有子 Agent 的用量，时间和 token 两项都看，哪个先到就停。

### 7.3 权限各管各的

默认不该全给，按最小权限来：做检索、做审查的只读；做实现的只能写自己的工作目录或分支；发消息、写生产数据、部署这类有副作用的操作，要么只留给主 Agent，要么要人确认。

### 7.4 链路追踪与分 Agent 记账

一个任务一个 trace ID，每个子 Agent 是其中一段，记下它收到的任务说明、调用的工具、交回的结果，用了多少 token、多少时间。出了问题才能定位是哪个 Agent 引入的错；成本也才能分到每个 Agent 头上。

### 7.5 评测：先有单 Agent 基线

做多 Agent 改进之前，先跑单 Agent 基线：

- **端到端评测**：同一批任务，单 Agent 基线和多 Agent 各跑几遍，比成功率或质量分、耗时、token 和费用。Agent 每次跑的结果都不一样，跑一遍不够。
- **分环节评测**：路由选对的比例，每个子 Agent 的完成率，Critic 判对的比例，汇总后的结论有多少能在子 Agent 的结果里找到依据。
- **起步不用大**：用大约 20 个代表真实用法的问题起步，用模型打分，也做人工测试。

## 八、新算力环境 vs 多 Agent：是基础设施，不是替代品

在 Codex 等 AI 编程助手中，让模型"创建一个新的算力环境"（沙盒、独立工作区）来处理特定任务，这种模式与多 Agent 架构在**目标和效果上非常相似，但本质上有明显区别**。严格来说，它属于「单智能体 + 隔离工具环境」（Single-Agent with Isolated Environment/Tool Use），是多 Agent 架构的底层基础设施，而非多 Agent 本身。

### 为什么它们看起来极其相似？

无论是开辟新算力环境还是引入新 Agent，核心目的都是解决三件事：

- **状态隔离与防污染**：将特定任务扔到全新环境中执行，保证主上下文的纯洁性，避免大模型"注意力稀释"或产生幻觉。
- **物理工作区边界**：新环境提供干净的内存空间、文件系统和依赖树，避免读写冲突。
- **任务降维**：将"大问题"拆解为"小问题"，在限定范围内求解，只把结果（而非过程）返回主控流。

### 核心差异：控制权与系统提示词在哪

区分两者的关键在于"控制权（Agency）"和"系统提示词（Persona/System Prompt）"归属谁。

**新算力/沙盒是被动的执行环境。** 当 AI 创建一个新环境跑代码时，环境里并没有另一个"独立思考的 AI"——依然是原来的主 AI 大脑在向新环境发送指令、写入代码、读取执行结果。这相当于一个程序员打开了一个新的虚拟机终端。交互语言是**代码与执行日志**。

**多 Agent 包含多个主动的思考节点。** 如果主控 Agent 召唤了一个"数据库专家 Agent"，这个子 Agent 拥有独立的 System Prompt、独立的思考循环（Thought/Action/Observation），遇到报错会自己决定如何修复，最后只把结论汇报给主 Agent。这相当于一个程序员把任务外包给了另一个专职的 DBA。交互语言通常是**自然语言或结构化 JSON 协议**。

此外，创建新算力主要实现的是**物理与状态隔离**（内存清空、变量重置、文件系统干净），而多 Agent 不仅需要物理隔离，更强调**逻辑与视角的隔离**——不同 Agent 拥有截然不同的 Prompt 和关注点，单靠一个"新算力环境"无法提供这种多维度的认知隔离。

### 总结

多 Agent 架构不是一道「要不要用」的选择题，而是一道「在什么条件下用、怎么用」的设计题。核心思路可以概括为：

- **拆**：上下文隔离、工具隔离、职责分离、并行加速——每种理由对应不同的拆分策略
- **通信**：主中转、黑板、直接对话——各有取舍，没有银弹
- **汇总**：字段化回传、证据绑定、独立检查——防止幻觉放大和决策冲突
- **工程**：失败兜底、预算管控、权限隔离、链路追踪、对照评测——让系统可观测、可调试、可度量

记住一个原则：比讲道理更有说服力的是对照数据。在决定引入多 Agent 之前，先跑通单 Agent 基线，用数据说话。

让 AI 新开一个环境去跑代码，是**利用工具隔离上下文**的优秀工程实践，相当于为单一智能体提供了一个"草稿本"或"隔离实验室"。只有当进入新算力环境的，是一个携带全新系统指令、拥有自主规划能力，并与其他环境中的 AI 进行对话协作的独立模型实例时，这个架构才真正进化成了多 Agent 系统。两者并不矛盾——隔离的算力环境，往往正是运行复杂多 Agent 协作的最佳底座。
