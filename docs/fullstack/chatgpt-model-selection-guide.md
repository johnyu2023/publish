在日常的 AI 辅助研发与复杂业务系统设计中，合理选择和切换 ChatGPT 的不同模型（如 Terra, Sol, Astra）不仅能大幅提升交付质量，还能有效管理额度与上下文窗口。本文将系统梳理 ChatGPT 的核心术语、模型消耗对比、场景选择及切换策略，为你提供一份即插即用的实战指南。

## 1. 核心术语与任务分类对齐

在与 AI 协同工作或编写提示词时，精准的术语能极大降低歧义，尤其应**完全避开单独使用“Session”**一词。以下是标准化术语中英对照表：

| 目标对象 / 概念 | 推荐术语 (中英对照) | 核心含义与场景示例 |
| :--- | :--- | :--- |
| **侧边栏里的一段聊天** | **会话 (Thread)** | 逻辑上的一个对话窗口，可包含多轮问答。 |
| **一次完整的问答交互** | **轮 (Turn)** | 从用户单次提问到 AI 的一次最终答复（期间可能包含多次隐式工具调用）。 |
| **跨越多个会话的持续目标** | **任务 (Work Item / Task)** | 具备明确业务目标的完整工作，如“股票停牌信息库与计算前置拦截”。 |
| **对某任务的局部修正** | **第 N 轮返修 (N-th Round Revision)** | 基于上一次交付物的修改，如“同一任务的第 1 轮返修审核”。 |
| **单次处理的文本容量** | **上下文窗口 (Context Window)** | 模型在单个 Thread 中能记住的历史信息上限，达到瓶颈时会触发自动压缩。 |
| **背景信息与约束集合** | **事实依据 (Ground Truth / Facts)** | 提供给 AI 的已确认业务规则、验收标准或不可推翻的前提条件。 |

> 💡 **最佳表达范例**：“请新建一个**会话 (Thread)**，但继续审核同一个跨会话**任务 (Work Item)**：`股票停牌信息库与计算前置拦截`。这是该任务的**第 1 轮返修 (1st Round Revision)**审核，不是新功能设计。”

## 2. 模型消耗速度与成本对比矩阵

模型的消耗通常分为**API 计费**与**订阅额度池消耗**两种逻辑，不可直接混为一谈。

### A. API Token 相对单价参考（以 Terra 为基准）
*注意：单价高不等于单任务绝对总价高，Astra 在复杂任务中可能以更少的输出 token 提前收敛。*

| 模型层级 | 输入价格 ($/M) | 输出价格 ($/M) | 相对 Terra 的价格倍率 (入 / 出) |
| :--- | :---: | :---: | :---: |
| **GPT-5.6 Terra** | 2 | 12 | 1× / 1× |
| **GPT-5.6 Sol** | 4 | 20 | 2× / 1.67× |
| **GPT-6 Astra** | 10 | 50 | 5× / 4.17× |

### B. Work/Codex 订阅额度消耗强度估算
*注意：每周额度和五小时额度同时生效，综合了上下文长度、工具调用、推理强度等因素，以下为同一任务下的近似消耗倍率：*

| 模型层级 | 相对 Terra 的额度消耗倍率 | 核心定位与匹配度 |
| :--- | :---: | :--- |
| **GPT-5.6 Luna** | ~ 0.1× | **极轻量**：极短对话、重复任务、提取、分类、措辞微调。 |
| **GPT-5.6 Terra** | 1× | **日常主力**：常规问答、基础代码编写、边界清晰的单轮审核。 |
| **GPT-5.5** | ~ 1.7–2.5× | **向下兼容**：特定旧模型兼容场景，或已验证其表现更佳时。 |
| **GPT-5.6 Sol** | ~ 2.0–2.5× | **进阶骨干**：跨模块推演、复杂逻辑实现、深度审查。 |
| **GPT-6 Astra** | ~ 4.5–5.0× | **最强推理**：高风险、完全陌生、极难推理的端到端问题。 |
| **Codex Spark (5.3)** | 独立池，不可换算 | **独立额度**：按其自身限额和界面提示使用。 |

## 3. 实际研发任务的模型首选与升级时机

在实际业务（如 QMT 量化交易系统、复杂并发系统）研发中，建议采用 **70% Terra + 25% Sol + 5% Astra** 的黄金配额策略。

| 研发工作阶段 / 任务类型 | 首选默认模型 | 🚀 何时考虑升级模型 (Trigger) |
| :--- | :--- | :--- |
| **需求澄清、术语释疑** | **Terra** (低/中档) | 仅简短文字可用 **Luna**；需追溯多份历史设计与代码事实时升 **Sol**。 |
| **架构推演、聊需求** | **Terra** (高档) | 涉及跨模块合同、事务边界、历史语义用 **Sol (高)**；关键业务规则定稿用 **Astra (中/高)**。 |
| **编写开发任务设计文档** | **Terra** (高档) | 涉及多阶段、多合同、前后端联动或数据迁移时升 **Sol (高)**。 |
| **拆分阶段、写阶段提示词**| **Terra** (高档) | 具有复杂依赖链、需预判未来返工路径时升 **Sol (高)**。 |
| **一轮返修审核与 Diff 核对**| **Terra** (高档) | 当任务仅需检查差异、跑聚焦测试、给 PASS/FAIL 且边界明确时。 |
| **深度代码审核与最终审计** | **Sol** (高档) | 涉及原子事务、隐性业务语义、跨数据库链路或最终的独立审计时，直接上 **Astra (高)**。 |

## 4. 模型切换与新建会话 (Thread) 的时机选择

提升模型能力**不等于**必须新建会话；但改变任务事实、交付物或审查视角时，**必须**新建会话。

### A. 基于任务边界的判断矩阵

| 当前场景状态 | 执行策略建议 |
| :--- | :--- |
| **仍在处理同一目标，只是发现难度增加** | 🟢 **留在原 Thread**，直接原地升级模型 (Terra → Sol → Astra)。 |
| **只是追问术语、补一两个约束条件** | 🟢 **留在原 Thread**，保持上下文连贯。 |
| **审核后按问题开始返修代码** | 🟡 **留原 Thread 或新开均可**；改动复杂时优先留原 Thread 保持代码脉络。 |
| **从需求讨论阶段转入正式写开发文档** | 🟠 **倾向于新建 Thread**，避免早期发散讨论干扰文档生成。 |
| **核心结论或前提被推翻 (如发现严重误解)** | 🔴 **必须新建 Thread**。附上“当前有效事实与新结论”，明确旧结论已作废。 |
| **需要独立视角的代码审核 / 验收** | 🔴 **必须新建 Thread**。附上验收标准、设计文档和审查范围，防止受原思路污染。 |

### B. 基于对话轮数 (Turns) 的实用规则

| 当前 Thread 轮数 | 操作建议 |
| :--- | :--- |
| **0 – 10 轮** | 绝不要仅仅因为轮数多而新建 Thread。 |
| **10 – 20 轮** | 若目标未变则继续。**技巧**：让模型先输出一份“当前事实、已定决策、未决问题”摘要作为锚点。 |
| **20 – 30 轮以上**| 检查是否跨越了研发阶段（如设计进入了测试）。若跨阶段，强烈建议新建 Thread。 |
| **任何轮数** | 只要发现历史记录中积累了**大量已作废结论**，立即止损并新建 Thread，效率远超原地纠错。 |

## 5. ⚠️ 核心注意事项与避坑指南

1. **不要试图用 Astra 在“被污染”的上下文中强行修补**：
   如果 Terra 已经产生了根深蒂固的错误业务理解（如：误将股票池快照当作资格条件），切到 Astra 往往无济于事。**最稳妥的做法**：新建 Thread，将正确的业务规则、明确禁止的旧理解一并丢给 Astra。
2. **谨慎使用最高推理档位 (xhigh)**：
   不要常态化开启最高推理档位。高推理不仅指数级消耗额度，在指令和事实文件不完整的情况下，反而容易导致模型“过度脑补”。官方准则：**先确保指令、文件和上下文完整，再提高推理强度。**
3. **把业务规则写死在 Prompt 里**：
   为了成本控制，在进行常规的 **Terra (high)** 审核时，尽量将关键的事务边界、调度逻辑等业务不变量“写死”在提示词中，降低模型自行推演产生的幻觉风险。
