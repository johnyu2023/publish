在日常的 AI 辅助研发与复杂业务系统设计中，合理选择和切换 ChatGPT 的不同模型（如 Terra, Sol, Astra）不仅能大幅提升交付质量，还能有效管理额度与上下文窗口。本文将系统梳理 ChatGPT 的核心术语、模型消耗对比、场景选择及切换策略，为你提供一份即插即用的实战指南。

## 模块一：基础认知与算力盘点

### 1. 核心术语与任务分类对齐

在与 AI 协同工作或编写提示词时，精准的术语能极大降低歧义，尤其应**完全避开单独使用“Session”**一词。以下是标准化术语中英对照表：

| 目标对象 / 概念 | 推荐术语 (中英对照) | 核心含义与场景示例 |
| :--- | :--- | :--- |
| **侧边栏里的一段聊天** | **会话 (Thread)** | 逻辑上的一个对话窗口，可包含多轮问答。 |
| **一次完整的问答交互** | **轮 (Turn)** | 从用户单次提问到 AI 的一次最终答复（期间可能包含多次隐式工具调用）。 |
| **跨越多个会话的持续目标** | **任务 (Work Item / Task)** | 具备明确业务目标的完整工作，如“股票停牌信息库与计算前置拦截”。 |
| **对某任务的局部修正** | **第 N 轮返修 (N-th Round Revision)** | 基于上一次交付物的修改，如“同一任务的第 1 轮返修审核”。 |
| **单次处理的文本容量** | **上下文窗口 (Context Window)** | 模型在单个 Thread 中能记住的历史信息上限，达到瓶颈时会触发自动压缩。 |
| **背景信息与约束集合** | **事实依据 (Ground Truth / Facts)** | 提供给 AI 的已确认业务规则、验收标准或不可推翻的前提条件。 |

> 💡 **最佳表达范例**：“请新建一个**会话 (Thread)**，但继续审核同一个跨会话**任务 (Work Item)**：`股票停牌信息库与计算前置拦截`。这是该任务的**第 1 轮返修 (1st Round Revision)**审核，不是新功能设计。”

### 2. 模型消耗速度与成本对比矩阵

模型的消耗通常分为**API 计费**与**订阅额度池消耗**两种逻辑，不可直接混为一谈。

## 模块二：实操策略——选型、升级与上下文管理

### 3. 实际研发任务的模型首选与升级时机

在实际业务（如 QMT 量化交易系统、复杂并发系统）研发中，建议采用 **70% Terra + 25% Sol + 5% Astra** 的黄金配额策略。

| 研发工作阶段 / 任务类型 | 首选默认模型 | 🚀 何时考虑升级模型 (Trigger) |
| :--- | :--- | :--- |
| **需求澄清、术语释疑** | **Terra** (低/中档) | 仅简短文字可用 **Luna**；需追溯多份历史设计与代码事实时升 **Sol**。 |
| **架构推演、聊需求** | **Terra** (高档) | 涉及跨模块合同、事务边界、历史语义用 **Sol (高)**；关键业务规则定稿用 **Astra (中/高)**。 |
| **编写开发任务设计文档** | **Terra** (高档) | 涉及多阶段、多合同、前后端联动或数据迁移时升 **Sol (高)**。 |
| **拆分阶段、写阶段提示词**| **Terra** (高档) | 具有复杂依赖链、需预判未来返工路径时升 **Sol (高)**。 |
| **一轮返修审核与 Diff 核对**| **Terra** (高档) | 当任务仅需检查差异、跑聚焦测试、给 PASS/FAIL 且边界明确时。 |
| **深度代码审核与最终审计** | **Sol** (高档) | 涉及原子事务、隐性业务语义、跨数据库链路或最终的独立审计时，直接上 **Astra (高)**。 |

### 4. 终极心法：模型与推理档位的平滑升级策略

在实际操作中，很多开发者会疑惑：“Terra 的「高」推理和 Sol 的「中」推理，到底哪个更强、哪个更耗额度？”

**结论先行**：**Terra「高」和 Sol「中」绝对不等价，且不存在官方固定的“额度换算比例”。** 它们都会消耗同一个「通用每周使用限额」，但实际扣减量综合了模型基础消耗、推理档位、任务步骤数、读写文件量及上下文长度。千万不要将其理解为“每发一条固定扣 1 格”。

#### A. 双维驱动：模型能力 vs 推理档位

要精准控制消耗，必须拆分理解两个核心维度：

1. **模型层级 (Model)**：决定了基础能力底线、速度与单位工作成本。在相同的 5 小时窗口内，预期可完成的任务数大致为：**Luna ≫ Terra ≈ 2～2.5 倍 Sol ≫ Astra**。
2. **推理档位 (Reasoning Level)**：决定了该模型为当前任务投入的“思考深度”。选择「较高」、「极高」或「Ultra」必然增加额度消耗，但**不保证结果一定更好**。如果上下文缺失、任务描述模糊或未给足文件权限，无脑拉高推理档位纯属浪费。

#### B. 核心模型定位与省流指南

除 Codex Spark 外，其余主模型均共享通用额度池。以下是各模型的精准定位：

| 模型选择 | 核心适用场景 (以 QMT 等复杂工程为例) | 额度管理与省流建议 |
| --- | --- | --- |
| **Luna** | 查找代码、提取信息、重复性小改、短文本。 | **极致省流**：先用它处理明确且低风险的细碎任务。 |
| **Terra** | 常规功能修改、单模块排查、一般测试修复。 | **日常首选**：默认使用「中」档，不够再升「高」档。 |
| **Sol** | 跨模块功能、较复杂业务逻辑、长链路分析。 | **关键攻坚**：核心开发任务默认「中」档，深挖时才用「高」档。 |
| **Astra** | 棘手 Bug、陌生架构、重要设计决策。 | **终极底牌**：留给真正卡住的问题，优先尝试「较轻」或「中」档。 |
| **GPT-5.5** | 较旧一代模型。 | 除非已验证其在特定任务表现更好，否则不建议优先选择。 |
| **Codex Spark** | 快速、轻量的局部编码工作。 | 💎 **独立额度池**：拥有单独的 5小时/每周额度，**不消耗通用池**！强烈推荐将细碎工作迁移至此。 |

#### C. 黄金法则：平滑升级的 S.O.P

最省额度的核心原则并不是“永远选最低端的模型”，而是：**用能一次成功的最低组合。** 用低阶模型反复报错返工三次，其消耗和时间成本往往远超用 Sol「中」档一次性解决。

强烈建议采用以下「递进式升级路径」，每次遇到瓶颈，**只升级一个维度**：

> 🟢 **Terra (中)** ➔ 🟡 **Terra (高)** ➔ 🟠 **Sol (中)** ➔ 🔴 **Sol (高)** ➔ 🟣 **Astra (较轻 / 中)**

* **常规起手 (Terra + 中)**：常规接口、前端组件、小范围 Bug、测试失败排查。
* **单点深化 (Terra + 高)**：单模块内具备一定复杂度，如交易逻辑边界、配置链路、较复杂的测试修复。
* **跨界梳理 (Sol + 中)**：跨前后端/数据库的多模块任务。切忌一上来就用高档，先让它做定位与首轮实现。
* **硬核重构 (Sol + 高)**：首轮不可靠、反复返工、需要复杂回归、涉及并发/状态机/隐蔽数据问题。
* **降维打击 (Astra + 较轻/中)**：彻底卡住或需要高质量技术判断时。注意：**Astra 的较低推理档位，往往强于 Sol 的高档位**，优先尝试跨模型而不是盲目死磕原模型的 Ultra 档。

**💡 避坑总结**：绝对不要从 `Terra (中)` 直接跳跃到 `Astra (Ultra)`。面对庞大的开发任务，最佳实践是：先用 Terra/Sol 完成范围确认和任务拆解，**最后只把最难的那一个子问题单独抛给 Astra**，这才是最高效的额度管理艺术。

### 5. 模型切换与新建会话 (Thread) 的时机选择

提升模型能力**不等于**必须新建会话；但改变任务事实、交付物或审查视角时，**必须**新建会话。

#### A. 基于任务边界的判断矩阵

| 当前场景状态 | 执行策略建议 |
| :--- | :--- |
| **仍在处理同一目标，只是发现难度增加** | 🟢 **留在原 Thread**，直接原地升级模型 (Terra → Sol → Astra)。 |
| **只是追问术语、补一两个约束条件** | 🟢 **留在原 Thread**，保持上下文连贯。 |
| **审核后按问题开始返修代码** | 🟡 **留原 Thread 或新开均可**；改动复杂时优先留原 Thread 保持代码脉络。 |
| **从需求讨论阶段转入正式写开发文档** | 🟠 **倾向于新建 Thread**，避免早期发散讨论干扰文档生成。 |
| **核心结论或前提被推翻 (如发现严重误解)** | 🔴 **必须新建 Thread**。附上“当前有效事实与新结论”，明确旧结论已作废。 |
| **需要独立视角的代码审核 / 验收** | 🔴 **必须新建 Thread**。附上验收标准、设计文档和审查范围，防止受原思路污染。 |

#### B. 基于对话轮数 (Turns) 的实用规则

| 当前 Thread 轮数 | 操作建议 |
| :--- | :--- |
| **0 – 10 轮** | 绝不要仅仅因为轮数多而新建 Thread。 |
| **10 – 20 轮** | 若目标未变则继续。**技巧**：让模型先输出一份“当前事实、已定决策、未决问题”摘要作为锚点。 |
| **20 – 30 轮以上**| 检查是否跨越了研发阶段（如设计进入了测试）。若跨阶段，强烈建议新建 Thread。 |
| **任何轮数** | 只要发现历史记录中积累了**大量已作废结论**，立即止损并新建 Thread，效率远超原地纠错。 |

### 6. ⚠️ 核心注意事项与避坑指南

1. **不要试图用 Astra 在“被污染”的上下文中强行修补**：
   如果 Terra 已经产生了根深蒂固的错误业务理解（如：误将股票池快照当作资格条件），切到 Astra 往往无济于事。**最稳妥的做法**：新建 Thread，将正确的业务规则、明确禁止的旧理解一并丢给 Astra。
2. **谨慎使用最高推理档位 (xhigh)**：
   不要常态化开启最高推理档位。高推理不仅指数级消耗额度，在指令和事实文件不完整的情况下，反而容易导致模型“过度脑补”。官方准则：**先确保指令、文件和上下文完整，再提高推理强度。**
3. **把业务规则写死在 Prompt 里**：
   为了成本控制，在进行常规的 **Terra (high)** 审核时，尽量将关键的事务边界、调度逻辑等业务不变量“写死”在提示词中，降低模型自行推演产生的幻觉风险。

## 模块三：高阶工作流：工作区生态分层与 Agent 协同

在复杂的项目实践（如 QMT 量化项目或大型全栈应用）中，仅靠切分模型是不够的，还需要结合架构工具进行合理分层。

### A. 最实用的生态分层矩阵

OpenAI 官方架构将项目指令、记忆、Skills、子 Agent 等视为互补层，而非互斥的工作方式。Git worktree 的核心价值则是让独立任务并行且不互相干扰：

| 层次结构 | 它解决什么问题 (核心功能) | ⚠️ 不应拿来替代什么 (防踩坑) |
| :--- | :--- | :--- |
| **项目 / Workspace** | 共享仓库、`AGENTS.md`、技能 (Skill)、工具、长期规则。 | **不能**指望它让不同对话“自动共享”全部的推断与决策过程。 |
| **Task / Thread** | 围绕一个 **明确交付物** 持续推理和执行。 | **不适合**塞入整个项目从头到尾的所有杂乱历史。 |
| **子 Agent** | 并行完成彼此独立、边界清楚的子问题。 | **不适合**处理强依赖、持续互相影响的交叉链路实现。 |
| **Worktree** | 隔离并发代码写入，避免不同任务互相踩文件。 | **不等于**自动提升系统设计质量。 |
| **Skill (技能)** | 固化反复出现的流程、约束和检查清单。 | **不应**把一次性的业务判断硬编码进去。 |

### B. 团队协同与架构共识

* **隔离污染**：不要把需求、设计、实现、报错、部署、审核无限塞进一个 task。项目变大后，作废的结论与不同阶段的上下文会发生严重的互相污染。
* **按需 Agent 化**：如果任务可并行且写入隔离，`子 Agent + Worktree` 效果极佳；但“为了多 agent 而多 agent”只会徒增系统协调成本和 Token 消耗。
* **流程技能化**：稳定不变的团队规矩（如“开发前必读文档”、“保护脏工作区”、“测试顺序”、“最终报告格式”）应做成 Skill，消灭重复提示词。
* **人类总控兜底**：总控 Agent 适合跑高度成熟的标准化流水线；但面对高风险业务项目，必须由人类牢牢把控 **设计批准权**、**阶段切换权** 与 **最终审核权**。

### C. 实战拆解：QMT 等复杂项目的任务切分法

不再按“前端 / 后端”机械拆分会话，而是严格按 **交付物和风险边界** 拆分：

1. **需求与设计 Task**：澄清核心业务语义，最终形成/修改设计合同。常规用 **Terra**，逻辑复杂上 **Sol**。
2. **实施 Task**：专注执行已批准的某单一阶段。强依赖环境下启用 **Worktree**，避免波及正在进行的其他功能修改。
3. **独立审核 Task (核心必做)**：**务必新开 Task**，绝不继承实施过程中的“心理路径”。只提供设计文档、验收条件、Diff 范围与测试结果。以 **Sol (高档)** 为主，面对高风险业务上 **Astra**。
4. **返修 Task**：针对最终审核清单做局部修改与回归。若边界明确，**Terra (高档)** 即可轻松应对。
5. **收敛子 Agent 权限**：仅在“可独立验证的事项”启用子 Agent（例如“扫描所有提交入口”、“核对前端路由与菜单”、“补充测试覆盖矩阵”）。**严禁**放任多个 Agent 同时修改同一业务主链路或同一组关键文件。

### D. 新开 Task 的标准“交接包”

**牢记**：同一项目下的新 Task 共享的仅仅是工作区代码和长期规则，而不是“你们之前的聊天记录”。每次新开 Task，都必须在开头给 AI 塞入一个结构化的“交接包”：

* 🎯 **当前目标**
* ✅ **已批准、不可推翻的业务事实**
* 🚧 **本次范围与严格禁止项**
* 📚 **本次必读文档**
* ⚠️ **当前工作区是否有未提交 (dirty) 的状态**
* 🧪 **验收与测试要求**

> 💡 **终极一句话工作法则：**
> **项目承载长期规则；Task 承载一个交付物；Skill 承载可复用流程；子 Agent 承载可并行子问题；Worktree 承载并发写入隔离；人类承载业务决策与最终裁决。**

## 附录：跨平台生态（Claude Code 等）的术语与机制映射

### 8. 跨平台生态下的术语差异（Claude Code vs ChatGPT）

在多工具协同的实际研发中，你可能会同时使用 ChatGPT、Codex CLI 以及 Claude Code。需要注意的是，**目前 AI 编码领域并没有一个所有厂商完全统一的术语标准**，各家叫法存在细微差异。

如果你需要在多个生态之间切换，或者编写跨平台的团队规范（如 `AGENTS.md`），请务必参考下方的跨平台术语对照表：

| 概念层级 | OpenAI 生态 (ChatGPT / API) | Anthropic 生态 (Claude Code) | 行业通用度与备注 |
| :--- | :--- | :--- | :--- |
| **单次完整的对话窗口** | **Thread** (官方 API 术语) / Chat | **Session** (官方标识如 `session_xxx`) | ⚠️ **存在分歧**。在 Claude Code 中，用户口头常说的 Thread 实际在系统底层被定义为 Session。不能直接混用。 |
| **一次“用户提问 → 助手回复”** | **Turn** | **Turn** (系统内置指令反复强调的词汇) | ✅ **高度通用**。无论是对话系统研究还是各家大厂的底层 Prompt，都通用此概念。 |
| **跨越多轮/多窗口的宏观目标** | 偏向自定义（常称 **Task**） | **Task** (有后台追踪状态) / **Agent** (派生独立会话) | ⚠️ **无强制统一标准**。这往往不是大模型强加的概念，而是依赖研发团队自己的组织方式（如“阶段 A”、“子任务 B”）。 |

#### 💡 跨平台团队协作的避坑建议

1. **交流时认准“Turn”**：当你需要限制 AI 的输出长度、干预步骤时，使用 **Turn**（轮）是最安全、最准确的业界通用词汇（例如：“Limit your analysis to this turn”）。
2. **入乡随俗的窗口称呼**：在 OpenAI/Codex 生态写提示词时用 **Thread**；而在 Claude Code 中排查日志或建立协调代理时，请认准 **Session** 标识。
3. **“任务 (Task)”需要自己定义边界**：既然各家对“跨窗口的更大任务”没有统一的强制指代，团队就必须在工程规范（如 Git Worktree 命名或项目根目录的规则文件）中明确“一个 Task 包含哪些交付物”，而不是指望大模型去自动理解你的项目宏观边界。

### 9. 深度解析：Claude Code 中的“Session”与额度重置机制

在使用 Claude Code 时，很多开发者会对 `/usage` 命令返回的 `current session` 感到困惑。因为在 Anthropic 的体系中，**“Session”这个词被重载了，用在了两个完全不同的概念上。**

#### A. 概念解耦：对话容器 vs 计费窗口

遇到“Session”一词，必须结合上下文来判断其真实含义，两者绝不能混淆：

1. **对话 Session（交互容器）**
   * **含义**：一个终端窗口里包含多个 Turn（轮）的一次完整多轮对话。
   * **证据**：Claude Code 系统底层生成的标识符即为 `session_xxx` 格式。
   * **生命周期**：当你执行 `/clear` 命令时，会清空当前终端的上下文历史，等同于开启了一次全新的对话交互。

2. **用量 Session（计费与限流窗口）**
   * **含义**：这是 Anthropic 订阅套餐（Pro/Max/Team）的**滚动时间限流窗口**。
   * **机制**：从你在这个窗口内产生第一次用量算起，以 **5 小时**为一个周期。周期内容量封顶，超限后必须等这 5 小时耗尽才会重置恢复。
   * **独立性**：这个用量窗口与你开了多少个终端对话、执行了多少次 `/clear` 毫无关系。网页版 (claude.ai)、桌面版 (Claude Desktop) 和终端 (Claude Code) **共享同一个用量池**。

#### B. 5 小时用量 Session 的容量差异

同样是“5 小时重置一次”，不同订阅套餐的可用消息额度差异巨大。以下是基于官方数据的容量倍数参考（实际条数受上下文长度和系统负载影响）：

| 订阅套餐 | 每 5 小时 Session 用量 (相对 Pro 倍数) | 容量预估与说明 |
| :--- | :--- | :--- |
| **Pro** | 1x (基准) | 高峰时段限额至少是免费版的 5 倍。 |
| **Team 标准席位** | 1.25x | 额度按“每个成员”**单独计算**，并非全团队共享。 |
| **Max 5x ($100/月)** | 5x | 大约每 5 小时至少 225 条消息。 |
| **Team 高级席位** | 6.25x | 同样按“每个成员”单独计算。 |
| **Max 20x ($200/月)**| **20x** | 大约每 5 小时至少 900 条消息。 |

> ⚠️ **关键注意**：
>
> 1. 上述表格中的“大约消息数”不是恒定值，官方声明其取决于消息长度、对话上下文深度及 Claude 当前的系统容量。
> 2. 除了这层滚动的 5 小时 Session 限额外，所有付费套餐还同时受到一个**跨全部模型的每周限额**约束。两者并存，任一触顶都会受限。
