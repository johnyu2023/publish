## 从程序员视角理解 QMT 的策略文件

> 可将其视为一个**由行情事件驱动的、具有特定生命周期的中间件容器**。

### 1. 核心钩子函数（Required Hooks）

QMT 策略文件本质上是一个遵循“约定大于配置”的 Python 模块。引擎会寻找以下两个关键进入点：

#### `init(ContextInfo)`

* **编程本质**：**构造函数/配置加载器**。
* **作用**：在进程启动或策略加载时仅执行一次。
* **资深视角**：用于初始化全局状态机（`ContextInfo` 对象）、预分配内存（如定义 `list` 或 `dict`）、订阅数据流（L2 数据必须在此预订）、设置交易参数（手续费、滑点）。
* **注意**：不要在这里写耗时过长的 IO 操作，否则会阻塞行情初始化。

#### `handlebar(ContextInfo)`

* **编程本质**：**事件循环的回调函数（Event Loop Callback）**。
* **作用**：由行情引擎根据你设置的“运行周期”被动触发。
* **资深视角**：它是策略的 `main_loop`。每当主图（Main Symbol）产生一个新的 Bar（K线）或 Tick（分笔），引擎就会将当前的快照压入 `ContextInfo` 并调用此函数。

---

### 2. 核心对象 `ContextInfo` 的本质

你可以把 `ContextInfo` 理解为一个**上下文单例指针**。

* **状态存储**：它是一个动态对象，你可以往它身上挂载任何自定义属性（如 `ContextInfo.my_position = 0`），这些属性在两次 `handlebar` 调用之间是**持久化**的（但在重启策略后会消失，除非使用了特定的全量存储接口）。
* **API 门面（Facade）**：它封装了所有底层复杂的 C++ 接口，包括：
  * **Data Access**: `get_market_data_ex` (时间序列数据库查询)。
  * **Trade Execution**: `passorder` (异步报单接口)。
  * **Status Query**: 账户资金、持仓、委托回报。

---

### 3. 回测 vs 运行：机制的“同”与“异”

这是很多程序员容易翻车的地方。QMT 设计的目标是 **“一套代码，双端运行”**，但其底层时钟驱动逻辑有显著差异：

#### 相同点

* **逻辑流一致**：函数调用顺序、`ContextInfo` 的属性访问逻辑完全相同。
* **数据结构一致**：无论是回测获取的成交历史，还是实盘获取的实时逐笔，返回的 `DataFrame` 结构保持高度统一。

#### 不同点（底层驱动差异）

| 维度 | 回测阶段 (Backtest) | 运行/实盘阶段 (Live) |
| :--- | :--- | :--- |
| **驱动源** | **历史数据库镜像**。 | **实时行情推送（Socket流）**。 |
| **时间轴** | 伪随机/离散时间。引擎会“瞬移”到每一根历史 K 线触发 `handlebar`。 | 真实物理时间。受网络延迟、交易所推送频率限制。 |
| **成交撮合** | **理想化模拟**。根据价格碰撞触发。 | **真实柜台撮合**。受买卖盘口深度、排单机制影响。 |
| **`is_last_bar`** | 只有回测序列的最后那根线返回 `True`。 | 每一秒钟跳动的最新数据均为 `True`。 |

---

### 4. 程序员视角的避坑指南

#### 1. 内存溢出风险
在回测时，如果你在 `handlebar` 里不停地往一个全局 `list` 里追加数据，回测 10 年的数据可能会产生数百万次追加，导致 Python 进程 OOM（内存溢出）。**实盘因为是实时触发，内存压力反而可能比回测小。**

#### 2. `handlebar` 的阻塞问题
`handlebar` 是单线程串行执行的。如果你在里面写了一个 `time.sleep(5)`，那么在这 5 秒内，所有的行情推送都会在队列中堆积。

* **资深方案**：如果需要处理大量数据，应考虑使用异步处理或将逻辑拆分。

#### 3. `is_last_bar` 的战略价值

```python
if not ContextInfo.is_last_bar(): return
```

* **回测时**：加上这一句，回测会瞬间完成（因为它跳过了中间 99% 的计算），只看最后结果。
* **实盘时**：必须加上，否则策略启动时会把过去 200 根历史 K 线全部当做“实时信号”重跑一遍，导致开盘瞬间疯狂下单。

## 订阅数据流（L2 数据必须在此预订）

> **`init` 里的订阅**：相当于在 Socket 编程中执行 `connect()` 和 `subscribe()`，建立数据管道。

从底层架构看，QMT 的行情引擎是一个**基于发布/订阅（Pub/Sub）模式**的异步系统。

* **资源预分配**：L2 数据（逐笔、全档）数据量极其庞大。如果你在 `handlebar` 这种高频回调里才去调用订阅，会导致引擎在处理每一跳 Tick 时都要进行一次网络握手和内存申请，这会造成严重的 I/O 阻塞。
* **缓存预热**：在 `init` 中预订，引擎会立刻开始在后台建立 WebSocket 链接并填充本地 Ring Buffer（环形缓冲区）。当你真正运行到 `handlebar` 需要数据时，它是从本地内存缓存中直接 `memcpy`，延迟最小。

**代码示例：**

```python
def init(ContextInfo):
    # 场景：监控 3 只股票的 L2 逐笔成交
    stock_list = ['600519.SH', '000858.SZ', '601318.SH']
    
    for stock in stock_list:
        # 核心：在初始化阶段就告诉引擎，我要这只票的 Level-2 逐笔流
        # period='l2transaction' 是 L2 专用的周期标识
        ContextInfo.subscribe_quote(stock, period='l2transaction')
        
    print("Pipeline established. L2 data streaming started in background.")
```

## `is_last_bar`：为什么实盘中还会有“历史数据”？

> **`is_last_bar`**：相当于在处理 Message Queue 时，判断 `msg.is_realtime` 标志位。如果是持久化存储里的旧消息（History），只更新状态不执行动作（Action）；如果是 Live 消息，才触发业务逻辑。

这是一个非常隐蔽的**“回放（Replay）”机制**，也是初学者最容易产生“幽灵下单”的地方。

### 核心矛盾：数据对齐
当你在 10:00:00 启动策略时，主图（比如上证指数）已经产生了今天的开盘 K 线，甚至包含了过去几年的历史 K 线。

* **引擎的行为**：为了保证策略逻辑的完整性（比如你的均线需要计算过去 20 天的数据），QMT 会**模拟**从过去某个时间点开始，把历史 K 线一根一根地丢进 `handlebar` 里跑一遍。
* **结果**：即使是实盘，在启动的一瞬间，`handlebar` 会被连续调用成百上千次。

#### 为什么 `tick` 模式下也有历史？
即使你选的是 `tick` 周期，QMT 为了让你能拿到 `count=500` 这样的历史切片，它在启动瞬间会把**当前已有的历史分笔数据**快速“过”一遍。

* **如果没有 `is_last_bar`**：
    假设 9:35 发生了一个金叉。你在 10:00 启动策略，引擎回放 9:35 的那根线时，你的逻辑会触发 `passorder`（下单）。**由于这是实盘环境，这个单子会真的发往交易所！** 结果就是你刚开机，策略就把早上的信号全部重补了一遍。
* **有了 `is_last_bar`**：
    它像一个**过滤器**。在回放历史数据时，`is_last_bar` 返回 `False`，直接 `return`；只有当引擎处理到**此时此刻**正在跳动的那一跳数据时，它才返回 `True`，允许下单逻辑执行。

## 策略运行时的`主图代码`和`运行周期`

对于资深程序员来说，理解 QMT 的“主图代码”和“运行周期”，最直观的方式是将其类比为 **分布式系统中的“时钟源（Clock Source）”** 和 **中断触发频率（Interrupt Frequency）**。

在 QMT 的底层架构中，你的 `handlebar` 函数并不是自顾自运行的 `while(true)` 循环，它是一个被动触发的 **Callback（回调）**。

---

### 1. 主图代码：策略的“硬件时钟源”

主图代码（Main Symbol）决定了**谁来踢你的代码一脚**。

* **编程本质**：它是 `handlebar` 事件监听的 **Subject（主题）**。
* **为什么需要它？**：在量化引擎中，为了保证逻辑同步，必须有一个基准标的。引擎会监听这个标的的行情包。
* **选指数（如 000001.SH）作为主图的逻辑**：
  * **高可用性**：指数在交易时间内永远有跳动，不会像个股一样因为没人买卖而“断流”。
  * **心跳包机制**：将指数作为主图，相当于建立了一个**稳定频率的心跳（Heartbeat）**。无论你监控的 20 只 Level-2 股票是否有成交，你的策略每秒都会被指数“唤醒”，去主动巡检那些个股的状态。

---

### 2. 运行周期：中断触发的“分频器”

运行周期决定了**时钟源跳动多少次，才调用一次你的 `handlebar`**。

#### Tick 周期（分笔）

* **机制**：**Raw Mode（原始模式）**。只要交易所推过来一个关于主图代码的数据包，引擎就立即执行 `handlebar`。
* **特性**：非定时的。行情波动快时，一秒钟可能触发 3 次；午休或死盘时，可能几秒钟才触发一次。
* **适用**：Level-2 高频监控、盘口瞬时大单捕获。

#### 分钟/日线周期（K线）

* **机制**：**Window Aggregation（窗口聚合）**。引擎会在内存中切分时间窗口（比如 5 分钟），只有当这一分钟的 K 线收盘（或更新）时，才触发一次回调。
* **适用**：传统的均线、MACD 等趋势策略。

---

### 3. “跨周期引用”：解耦时钟源与数据源

这是程序员最容易混淆的一点：**主图周期并不限制你获取的数据周期。**

* **场景**：你希望在 **Tick 级别（实时）** 运行，但逻辑是判断 **日线（1d）** 是否金叉。
* **实现**：
    1. 设置运行周期为 `Tick`。
    2. 在 `handlebar` 内部使用 `ContextInfo.get_market_data_ex(..., period='1d')`。
* **资深视角**：这相当于在一个 `high_resolution_timer`（高精度定时器）中断里，去查询一个 `low_resolution_database`（低频数据库）。这样做能保证你在日线信号出现的**那一毫秒**就完成下单，而不是等到日线收盘。

---

### 4. 为什么实盘必须写 `if not ContextInfo.is_last_bar(): return`？

作为程序员，你可以把这个逻辑理解为 **“冷启动时的历史增量同步”**。

当策略启动（Start）时：

1. **历史重放（Replay）**：引擎为了帮你构建内存中的技术指标（如 20 日均线），会把过去的历史 K 线（Bars）极速“泵”入 `handlebar`。
2. **状态冲突**：如果没有这行判断，你的策略会认为这成千上万根历史线都是“刚刚发生的”。
    * *后果*：如果 3 天前有个买入信号，策略在启动瞬间重放 3 天前的 Bar 时，会**真的发出一个实盘买单**。
3. **Gatekeeper（守门员）**：`is_last_bar()` 在重放阶段返回 `False`，在到达“此时此刻”的实时流时返回 `True`。

## 策略启动瞬间的`历史回放`与`信号漂移`问题

> **QMT 的数据驱动模型是“流式回放”而非“断点续传”。**

> 实盘运行某个策略，主图设为 000001.SH，周期设为 tick。在10:00启动该策略，监听某个股大单的触发。如果曾在9:45发生过该个股大单触发，会否在10:00启动的策略后，快速推送这个9:45发生过的数据吗？

### 1. 数据的“流式回放”机制
当你 10:00 启动策略，主图设为 `000001.SH` (Tick 周期) 时：
1. **冷启动同步**：QMT 引擎为了让你的策略能够计算技术指标（比如 20 笔均价），它不会只给你 10:00 之后的那一秒数据。
2. **数据泵入**：引擎会从本地缓存中，把 10:00 之前的一部分 Tick 数据（通常是当天已产生的全部或最近一段）**极速“泵”入**你的 `handlebar` 函数。
3. **9:45 的数据去向**：如果你在 `handlebar` 里调用 `get_market_data_ex(..., period='l2transaction', count=500)`：
   * **启动瞬间**：`handlebar` 会被连续调用（频率远超 1秒/次），此时它会读到包含 9:45 在内的历史逐笔数据。

---

### 2. `if not ContextInfo.is_last_bar(): return` 的“闸门”作用
这就是为什么我们反复强调这行代码。

* **如果没有这行代码**：
  在 10:00 启动的一刹那，引擎回放 9:45 的那一跳数据时，`handlebar` 被执行。你的代码逻辑发现“9:45 有大单”，于是立即触发 `passorder`。
  **结果**：你在 10:00 补了一个 15 分钟前的单子。这就是典型的`信号重影`。

* **如果有这行代码**：
  引擎回放 9:45 的数据时，`is_last_bar()` 返回 `False`。你的逻辑直接 `return`，不进行大单检测，也不下单。
  直到引擎处理到 10:00:01 那个真正的实时 Tick 时，`is_last_bar()` 返回 `True`，逻辑才开始生效。
  **结果**：9:45 的大单被**静默过滤**掉，策略只监控 10:00 之后的实时机会。



---

### 3. Level-2 逐笔数据的特殊性：`count` 参数的影响
即便你写了 `is_last_bar`，还有一个“数据窗口”的问题：

你在 10:00:01 第一次真正运行逻辑时，执行了：
`data = ContextInfo.get_market_data_ex(..., count=500)`

* **数据构成**：由于这 500 笔是**回溯**的，这 500 笔里极大概率包含了 9:55 甚至 9:45 的数据。
* **逻辑陷阱**：如果你的代码是“遍历这 500 笔并计算净买入”，那么 9:45 的大单依然会被计算在内。
* **正确做法**：在 10:00 启动后的第一个 Tick，你应该记录下当前的**最大成交序号 (tradeIndex)** 或 **最后时间戳**。后续只计算 `tradeIndex` 大于启动时刻的增量数据。

---

### 4. 程序员视角的总结

1. **会推送吗？** 底层数据接口（Data API）**会**提供 9:45 的数据，因为它要填满你的 `count=500` 缓冲区。
2. **会触发 `handlebar` 吗？** **会**。引擎会通过回放（Replay）模式快速调用 `handlebar` 处理 9:45 的 Bar。
3. **会误下单吗？** 取决于你有没有用 `is_last_bar` 挡住。没挡住就会补单。
4. **会直接抛弃吗？** 引擎不会主动抛弃（为了保证指标计算连续性），除非你的代码逻辑（通过 `is_last_bar` 或时间戳对比）主动将其抛弃。

### 💡 实战建议
如果你只想监控“从 10:00 启动这一刻起”发生的大单：
1. 必须使用 `if not ContextInfo.is_last_bar(): return`。
2. 在 `init` 中记录一个 `ContextInfo.start_time = time.time()`。
3. 在大单判断逻辑里，增加一个时间过滤：`if tick_time < ContextInfo.start_time: continue`。
