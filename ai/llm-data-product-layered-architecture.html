标题：LLM数据产品的分层解耦架构
描述：一些零碎的知识
发布日期：2026/08/08
标签：

分层架构的本质，是将“计算（Computing）”和“推理（Reasoning）”彻底分开。这其实是对经典软件工程原则（高内聚、低耦合）在 AI 时代的重申：让确定性的代码去处理 IO、内存和数据流，让概率性的 LLM 专注于做高阶的语义萃取和决策。

缘起 ​

在传统的软件工程中，我们习惯了MVC或者更现代的前后端分离、微服务架构。数据层、业务逻辑层和表示层之间有着严格的物理或逻辑隔离。然而，当我们将大语言模型（LLM）引入数据产品时，确定性的代码逻辑与概率性的自然语言推理发生了碰撞，从而引发了所谓的LLM分层架构问题。

从“上帝提示词”到“架构解耦” ​

在LLM应用开发的早期，开发者往往容易陷入一种“单体架构”的陷阱：将数据获取、业务规则、意图识别和格式化输出全部塞进一个超大的Prompt（提示词）中，直接交给LLM处理。

这种高度耦合的“上帝模型”模式会带来几个致命问题：

  1. 上下文膨胀与成本失控： 将原始的结构化数据（如海量的JSONL日志、逐笔Tick数据流）直接丢给LLM，不仅会迅速耗尽Token窗口，还会导致高昂的API成本。
  2. 延迟瓶颈： LLM的推理速度（尤其是长文本流式输出）远低于传统的代码执行。如果数据过滤和指标聚合这种本可以由代码瞬间完成的工作也交给LLM，系统的整体延迟将无法忍受。
  3. 不可靠与脆弱性： LLM本质上是概率模型。如果依赖LLM去保证输出的数据结构（如严格的JSON格式）或者进行精确的数学计算，一旦模型产生幻觉，整个下游的数据管道就会崩溃。

现代 LLM 数据产品的分层参考架构 ​

为了解决上述问题，目前的行业最佳实践是将LLM作为架构中的一个功能节点，而不是整个系统的大脑。一个成熟的LLM数据产品通常会采用以下严格解耦的分层设计：

架构层级核心职责技术特征与实现方式
表示层 (UI Layer)用户意图捕捉与结果呈现通常为 React/Vue 等前端框架，仅负责展示和接收指令，不包含核心业务逻辑。
接入与网关层 (API Layer)会话管理、鉴权、路由使用 FastAPI、Spring Boot 等处理请求，维护多线程并发和长链接。
操作编排层 (Orchestration)流程控制、多模型/Agent协同系统的真正大脑。 在这里进行任务边界的划分，例如将高级设计交给模型A，将复杂的代码生成交给模型B。
LLM 增强/特征提取层数据压缩、上下文构建最关键的“降噪”层。 在将数据喂给LLM前，先通过代码聚类高频信号、剔除低价值数组，将其浓缩为高密度的 Markdown 报告。
基础数据层 (Data Engine)数据清洗、存储、实时分发纯确定性环境。使用 SQLite/PostgreSQL 存储持久化数据，利用 ZeroMQ 等消息队列进行数据引擎与后台进程的单向解耦推送。
LLM 推理层 (LLM Layer)纯粹的语义理解与推理只接收经过高度压缩和格式化的高质量上下文，输出最终的决策或文本结果。

举例说明：量化行情监控系统的架构演进 ​

假设我们要开发一个“实时股票异动分析助手”。用户提问：“分析一下今天上午某概念板块的资金净流入趋势，并给出操作建议。”

反面模式（未分层的强耦合） ​

系统接收到请求后，直接通过 API（如 Tushare 或 QMT）拉取该板块所有股票上午的实时 Level 2 逐笔交易明细。然后，系统将这些几兆大小的原始数据强行拼接成一个巨大的 Prompt 发送给 LLM：“这是上午的原始交易数据，请计算资金净流入并分析趋势。”

  • 结果： 内存暴涨、Token 超限直接报错；即使没有报错，LLM 的数学计算也会出错，且响应需要几十秒，完全失去“实时监控”的意义。

正确模式（深度解耦的分层架构） ​

  1. 数据与指标层（确定性计算）： 后台的守护进程通过 ZeroMQ 实时接收行情引擎推送的数据，并使用 Python 代码完成时间聚类算法，计算出“大单净流入”、“5日/20日日均成交量 (ADV)”等高阶指标。这部分坚决不让 LLM 参与。
  2. 特征提取与增强层（数据降维）： 系统将上述计算好的指标数据进行二次过滤，剥离掉低价值的数组块，提取出关键特征，并将其组装成一段高密度的结构化 Markdown 文本（例如：## 板块资金异动报告 \n **核心指标：** 大单净流入 5.2亿...）。
  3. 编排与推理层（多模型分发）： FastAPI 后端将压缩后的高质量 Markdown 报告以及用户的提问发送给指定的 LLM。LLM 不再需要“计算”数据，它只需要发挥其擅长的“推理”能力，根据各项指标的变化趋势，输出专业的文字分析和操作建议。

2层LLM调用方案 ​

2层（甚至多层）LLM调用方案在当前复杂的企业级 AI 应用中非常合理，且已经成为一种主流的设计模式（Design Pattern）。

在软件架构中，我们强调用不同的工具解决不同粒度的问题。将这种思维平移到 AI 开发中，就是通过构建结构化的多模型工作流，将不同的任务边界映射到不同的模型实例上。

为什么 2 层 LLM 调用是合理的？ ​

单次 LLM 调用的最大瓶颈在于既要又要：既要求模型有极快的响应速度（低延迟），又要求它能处理海量上下文，还要求它具备极高的逻辑推理和代码/指令生成能力。这在工程上是不切实际的。

引入 2 层 LLM 调用的核心逻辑在于职责分离（Separation of Concerns）：

  1. 成本与速度的平衡： 并非所有任务都需要调用最昂贵、最慢的推理大模型。
  2. 上下文窗口管理： 利用 Map-Reduce 思想，将超长文本或海量日志先降维，再汇总。
  3. 消除幻觉与自我校验： 用一个模型生成，用另一个模型去审查和纠偏。

常见的 2 层 LLM 架构模式 ​

在实际的工程实践中，2 层 LLM 调用通常有以下几种经典的组合形态：

1. 路由与意图分发模式 (Router / Gatekeeper) ​

这是最常见的第一梯队方案，旨在保护核心计算资源不被滥用。

  • Layer 1 (轻量级模型)： 负责意图识别、参数提取、或者决定是否需要调用外部工具（Agent Router）。它必须极快、成本极低。
  • Layer 2 (重型推理模型)： 只有当 Layer 1 判定请求涉及复杂的业务逻辑时，才将组装好的 Prompt 发送给 Layer 2 处理。

2. 规划者与执行者模式 (Planner & Worker) ​

这种模式完美契合复杂工程的开发与实施流。

  • Layer 1 (架构师/规划者)： 负责高层设计（High-level Design），将一个宏大的目标拆解为多个子任务（Task Breakdown）。
  • Layer 2 (工程师/执行者)： 接收拆解后的具体子任务，专注于复杂的多文件工程代码编写或底层配置微调。这种边界清晰的协作框架，能极大降低复杂系统的出错率。

3. 生成与评估模式 (Generator & Evaluator) ​

在对输出质量要求极高的场景（如量化交易策略生成、底层数据转换）中，单次生成的风险过高。

  • Layer 1 (生成器)： 负责根据输入快速生成初稿、代码或 SQL 语句。
  • Layer 2 (评审员)： 拿回 Layer 1 的输出，根据预设的严格规则（如语法规范、安全准则）进行 Review。如果发现错误，甚至会驳回让 Layer 1 重写（形成闭环）。

4. Map-Reduce 降维提纯模式 (Data Synthesizer) ​

当我们需要处理大规模的离线历史回测数据或连续的 JSONL 日志时，单次请求极易突破 Token 限制并导致内存膨胀。

  • Layer 1 (Map 节点)： 并发处理切片后的原始数据段，剔除低价值数组块，聚类高频信号，将它们分别压缩为高密度的 Markdown 报告。
  • Layer 2 (Reduce 节点)： 汇总所有 Layer 1 产出的高密度报告，进行全局的逻辑推理和最终结论生成。
