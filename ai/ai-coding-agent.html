标题：AI Coding Agent 使用心得
发布日期：2026/04/17
标签：
Coding Agent

很多人在用“大炮轰蚊子”，而且是用“最贵的金弹头”去轰一群蚊子。

Agent 模式 vs. 自动化脚本模式 ​

你说得非常对，这其实是目前很多开发者在使用 AI Coding Agent（如 Claude Code, Cursor, Windsurf）时的一个典型“消费误区”。

简单来说，他的意思是：很多人在用“大炮轰蚊子”，而且是用“最贵的金弹头”去轰一群蚊子。

以下是这段话的详细拆解：

1. 核心矛盾：Agent 模式 vs. 自动化脚本模式 ​

对比两种处理大量同类文件（比如给 100 个代码文件加注释，或者重构 50 个接口）的方式：

模式 A：直接让 Coding 模型处理（Claude Code 方式） ​

  • 做法： 你对 Claude Code 说：“帮我把这个文件夹里所有的 Python 文件都改成异步调用。”
  • 代价： Claude 会反复读取文件、思考、尝试修改、运行测试、报错、再读取。因为 Claude Code 这种 Agent 是为了解决复杂逻辑设计的，它每一步都会携带大量的上下文（Context Window），导致 Token 消耗极快。
  • 结果： 还没改完几个文件，你的额度（套餐）就见底了。

模式 B：编写 Python 脚本 + 调用 LLM API（这种更聪明） ​

  • 做法： 你先花 5 分钟让 Claude 帮你写一个 Python 脚本。这个脚本的功能是：遍历文件夹 -> 读取单个文件内容 -> 调用便宜的 API（如 Claude 3.5 Haiku 或 GPT-4o-mini）-> 按照既定模板处理 -> 保存。
  • 代价： 你只在编写脚本时消耗了一点点高性能模型的 Token。后续的大规模处理运行的是本地代码，API 调用也是按需付费，没有 Agent 模式下沉重的“思考成本”。
  • 结果： 处理 1000 个文件可能也就花几块钱，而且速度极快，完全可控。

2. 为什么这样是“没底”且“不可行”？ ​

  • 没底（成本不可控）： Agent 模式是“黑盒”操作。你不知道它为了改一个文件会反复读取多少次上下文。对于同质化的重复劳动，Agent 的智能是一种浪费。
  • 不可行（规模化难题）： * 上下文溢出： 如果文件很多，Agent 的对话上下文会越来越长，最后导致模型“变笨”或者报错。
    • 效率低下： 脚本可以多线程并发处理，而 Agent 通常是一个一个文件磨洋工。

3. 总结 ​

维度直接用 Claude Code 处理多文件Python 脚本 + LLM API
适用场景解决复杂的、跨文件的逻辑 Bug处理大量同类、结构化的任务
成本消耗极高（全量上下文 + 高级模型费率）极低（仅针对目标数据付费 + 低价模型）
可控性较低（AI 可能自由发挥）极高（逻辑由 Python 代码锁定）
建议适合“攻坚战”适合“扫荡战”
